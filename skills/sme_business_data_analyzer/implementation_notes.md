# SME Business Data Analyzer — Implementation Notes

## Overview

The SME Business Data Analyzer Skill is implemented as a single Python file (`scripts/sme_analyzer.py`, ~1,599 lines) using pandas. This document describes the implementation architecture, the relationship to predecessor files, and the technical decisions that govern its behavior.

---

## Relationship to rootiq_analyzer.py and rootiq_metrics.py

Three Python files form the implementation lineage:

### rootiq_metrics.py (483 lines, openpyxl)

This is the **original reference implementation** of the 28-metric calculation specification (M01-M28). It uses openpyxl directly (not pandas) and was produced during the calculation-spec design phase. Its purpose was to:

- Validate that the calculation spec is implementable
- Produce machine-computed reference values (`rootiq_metric_reference_values.json`)
- Serve as a correctness oracle — every value in the spec's reference table was generated by this script

It is **not used at runtime** by the Skill. It remains in the workspace as a reference oracle for cross-validation.

### rootiq_analyzer.py (1,070 lines, pandas)

This is the **first pandas-based implementation**, created as the reusable `RootIQAnalyzer` class. It was the direct predecessor of the Skill's `sme_analyzer.py`. Key differences from `rootiq_metrics.py`:

- Uses pandas instead of openpyxl for data loading and manipulation
- Supports both Excel and CSV input
- Has a cleaner dataclass-based API (`source`, `baseline_period`, `current_period`, `out_dir`)
- Adds duplicate-row detection and sentinel-value handling

This file was the basis for packaging as a WorkBuddy Skill.

### sme_analyzer.py (1,599 lines, pandas) — The Skill Implementation

This is the **production Skill implementation**, adapted from `rootiq_analyzer.py`. It is the file that ships inside the Skill package at `scripts/sme_analyzer.py`. Enhancements over `rootiq_analyzer.py`:

| Enhancement | Description |
|---|---|
| Profit metrics | When `Sales` has `unit_cost`, `cogs`, `gross_profit` columns, computes per-product and overall COGS, gross profit, gross margin %, and average unit cost |
| Profit anomaly rules | 4 new rules: gross profit decline, gross margin decline, COGS increase, sales unit cost increase |
| Operations metrics | Full rewrite for Scenario 3 Operations schema: `actual_staff`, `required_staff`, `capacity_orders`, `orders_fulfilled`, `avg_fulfilment_hours` with per-shift breakdown |
| Operations anomaly rules | 2 new rules: ops staff shortfall, ops fulfilment rate decline |
| CSV input | Supports directory of CSVs, single CSV, or list of CSV paths with case-insensitive filename matching |
| CLI period args | `--baseline-start`, `--baseline-end`, `--current-start`, `--current-end` |
| Duplicate detection | Checks primary key duplicates and full-row duplicates per sheet |
| Enhanced data quality | Reports detected datasets, unexpected sheets, sentinel NaN values |
| Identity checks | `cogs == quantity * unit_cost` and `gross_profit == revenue - cogs` added |
| Backward compatibility | Legacy Operations column names (`staff_count`, `operational_capacity_pct`, `fulfilment_time_hours`) supported as fallbacks |

## Baseline/Current Period Handling

### Default Periods

```python
DEFAULT_BASELINE = (date(2026, 8, 3), date(2026, 8, 30))  # 28 days, inclusive
DEFAULT_CURRENT  = (date(2026, 8, 31), date(2026, 9, 27)) # 28 days, inclusive
```

Both windows are inclusive on both ends, adjacent (no gap), and equally long (28 days). No day-count normalization is required for level metrics.

### Period Assignment

Each sheet has a designated primary date column used for period tagging:

| Sheet | Primary Date Column | Rationale |
|---|---|---|
| `Sales` | `date` | Transaction date |
| `Inventory` | `date` | Daily snapshot date |
| `Customer_Feedback` | `date` | Feedback date |
| `Purchase_Orders` | `request_date` | PO belongs to period in which it was raised |
| `Operations` | `date` | Daily operations record |
| `Suppliers` | none | Pre-aggregated table, no date column |

Every row is tagged `BASELINE`, `CURRENT`, or `OUTSIDE`. `OUTSIDE` rows are counted and reported in data quality warnings — never silently dropped.

### Period Days

```python
bd = (b1 - b0).days + 1  # inclusive
cd = (c1 - c0).days + 1
self._period_days = max(bd, cd)
```

Used as the denominator for average stockout hours and availability calculations (calendar days, not data-row count).

## Anomaly Detection Rules

19 rules, each with a type, threshold, and relevance weight:

### Rule Types

| Type | Logic |
|---|---|
| `pct_le` | Flag if `pct_change <= threshold` (decline detection) |
| `pct_ge` | Flag if `pct_change >= threshold` (increase detection) |
| `pp_le` | Flag if `pp_change <= threshold` (percentage-point decline) |
| `stockout` | Flag if `current >= 2 * baseline` OR (`baseline == 0` AND `current > 8h`) |
| `approval` | Flag if `current > 2 days` OR `current > 1.5 * baseline` |
| `mult_gt` | Flag if `current > threshold * baseline` |

### Base-Zero Handling

When baseline is 0 and current > 0, several rules (`complaint_rate`, `refund_rate`, `late_orders`, `ops_late_orders`) use a fallback: flag if `pp_change > 0` (absolute increase from zero is itself an anomaly).

### Composite Score

```
score = magnitude_ratio * relevance_weight * 10
```

Where `magnitude_ratio = abs(pct_change) / abs(threshold)` (or `abs(pp_change) / abs(threshold)` for pp-based rules).

### Full Rule Table

| Rule | Type | Threshold | Relevance | Label |
|---|---|---|---|---|
| `revenue` | pct_le | -10.0% | 10 | Revenue decline |
| `product_revenue` | pct_le | -15.0% | 9 | Product revenue decline |
| `stockout_hours` | stockout | 2x / 8h | 8 | Stockout hours surge |
| `po_approval_time` | approval | 2d / 1.5x | 7 | PO approval time spike |
| `supplier_lead_time` | mult_gt | 1.5x | 7 | Supplier lead-time increase |
| `unit_cost` | pct_ge | +10.0% | 5 | Unit-cost increase |
| `complaint_rate` | pct_ge | +50.0% | 6 | Complaint-rate increase |
| `refund_rate` | pct_ge | +50.0% | 6 | Refund-rate increase |
| `fulfilment_time` | pct_ge | +30.0% | 7 | Fulfilment-time increase |
| `late_orders` | pct_ge | +50.0% | 7 | Late-order increase |
| `ops_capacity` | pct_le | -15.0% | 6 | Operational capacity drop |
| `ops_fulfilment` | pct_ge | +30.0% | 7 | Operations fulfilment-time increase |
| `ops_late_orders` | pct_ge | +50.0% | 7 | Operations late-order increase |
| `gross_profit` | pct_le | -10.0% | 9 | Gross-profit decline |
| `gross_margin` | pp_le | -3.0pp | 8 | Gross-margin decline |

## Data Validation

### Schema Validation

Each sheet is checked against its expected column list (`EXPECTED_SHEETS`). Missing required columns generate a data-quality warning but do not halt execution.

### Date Parsing

Dates are parsed via `_to_date()`, which handles:
- `datetime` objects (from pandas Excel reader)
- `date` objects
- Excel serial numbers (via `datetime(1899, 12, 30) + timedelta(days=int(val))`)
- String formats: `%Y-%m-%d`, `%Y/%m/%d`, `%d-%m-%Y`, `%d/%m/%Y`, `%m/%d/%Y`, `%Y%m%d`, and ISO 8601

Unparseable dates are reported as invalid values.

### Numeric Coercion

Numeric columns are coerced via `_safe_num()`, which returns `None` for non-numeric values. Non-numeric values in numeric columns are reported as invalid values.

### Sentinel Value Detection

Excel text "None" in specific columns (currently `Customer_Feedback.complaint_type`) is detected as a sentinel value. Pandas reads these as `NaN`. The analyzer distinguishes between true missing values and sentinel values, reporting the latter as a warning rather than a missing value.

### Data Quality Identities

Five identity checks are run on every load:

1. `revenue == quantity * unit_price` (Sales)
2. `cogs == quantity * unit_cost` (Sales, if profit columns present)
3. `gross_profit == revenue - cogs` (Sales, if profit columns present)
4. `closing_stock == opening_stock + received - sold` (Inventory)
5. `approval_days == approval_date - request_date` (Purchase_Orders)

Mismatches are reported as data-quality warnings.

### Duplicate Detection

Primary key duplicates and full-row duplicates are checked for `Sales`, `Purchase_Orders`, `Customer_Feedback`, and `Suppliers`.

## Error Handling

### Missing Optional Sheets

If a sheet is not present in the workbook, its metrics section is `[]` in the output. The analyzer continues with available sheets. No error is raised.

### Missing Required Columns

If a sheet is present but missing required columns, a data-quality warning is generated. The analyzer attempts to compute what it can with available columns and skips metrics that need the missing column.

### Unparseable Dates

Reported as invalid values in `data_quality.invalid_values`. The row's period tag becomes `UNKNOWN`, and it is excluded from metric calculations.

### Non-Numeric Values

Reported as invalid values. The value becomes `None` and is excluded from aggregations.

### Division by Zero

Handled by `_pct_change()`:
- If `base == 0`: returns `(None, True)` — null value with `base_zero = True` flag
- If `base is None` or `cur is None`: returns `(None, False)` — null value without flag

Never raises an exception, never returns 0/100/inf.

### Empty Groups

If no rows exist for a period (e.g., all rows are OUTSIDE), aggregates return `None`. The metric is still emitted with `null` values.

## Known Limitations

1. **No slope/regression computation.** The calculation spec (M13) calls for OLS slope of closing stock over time, but the implementation uses average closing stock and percentage change only. Slope is not computed.

2. **No PO-level delay histogram.** The spec (M18) calls for a full delay histogram. The implementation computes late-order count and mean delay but does not emit a distribution histogram.

3. **No statistical abnormality test.** The spec (M19) calls for a `delay > mean + 2*stdev` test. Since baseline delays are all 0 (stdev = 0), this test degenerates. The implementation uses only the absolute threshold test.

4. **Suppliers table has no date column.** Lead time and unit cost changes are taken as two-point differences from pre-aggregated `baseline_*`/`current_*` columns. No period-based attribution is possible. Flagged with `no_period_split`.

5. **Customer_Feedback has no order_id.** All rates use `feedback_records` as the denominator, not order count. This is a data schema limitation, not an implementation choice.

6. **Sales has no supplier_id.** Supplier attribution passes through `product_id` → `Suppliers` (1:1 mapping). This is lossless for the current dataset but would not generalize.

7. **No volume-weighted cost attribution.** Unit cost exists only as a two-point pair in `Suppliers`. Cannot be attributed to specific POs or dates.

8. **Operations legacy schema fallback.** Old column names (`staff_count`, `operational_capacity_pct`, `fulfilment_time_hours`) are supported but produce different metric names (`avg_staff_count`, `avg_operational_capacity_pct`) than the primary schema.

9. **No event-level timestamp granularity.** Period assignment is at the day level. Sub-day causal timing (e.g., did the staff reduction happen before or after the complaint surge?) cannot be determined from this data.

## Compatibility with analysis_summary.json

The output file is always named `analysis_summary.json` and written to the output directory (default: same directory as the source file). This filename is a stable contract:

- Downstream consumers (RootIQ Mapper, Orchestrator, handoff JSON creation) read this exact filename.
- The JSON structure has been stable across all three RootIQ scenarios (S1: revenue decline, S2: profit margin decline, S3: complaints/operations).
- Backward-compatible aliases (`current`/`change_pct` in anomalies) ensure older consumers continue to work.
- New optional fields (profit metrics, operations metrics) are added as additional sections or `null` values — never by removing or renaming existing fields.
- The CSV output (`analysis_summary.csv`) uses the same directory and a flat structure for easy spreadsheet import.

### Cross-Scenario Validation

The implementation was independently audited (108 automated cross-validation checks across all three scenarios) with the result: **PASS** — 0 errors, 0 blocking warnings, 6 informational warnings. All metric values are reproducible from the source workbooks.
